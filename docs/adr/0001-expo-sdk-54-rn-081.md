# 0001. Expo SDK 54 and React Native 0.81

- Status: Accepted; its binding reason has lapsed
- Date: 2026-09-18

> Note, 2026-09-19: the constraint below was react-native-macos, and
> [0011](0011-mac-via-the-ipad-build.md) deleted that target. Nothing forces SDK 54 any more, and the
> `overrides` entry this record calls for has been removed — with react-native-macos gone it changed
> no resolution. The pin itself was deliberately left alone: an SDK bump is its own piece of work,
> planned rather than slipped in, which is what this record already says.

## Context

Hermie targets iOS, iPadOS, Android and macOS from one codebase. Expo gives us the module ecosystem,
the build tooling and continuous native generation on iOS and Android. macOS is not an Expo platform;
it comes from react-native-macos, which tracks React Native upstream at its own pace.

At the time of writing:

- react-native-macos publishes 0.81.9. There is no 0.82 or later release.
- Expo SDK 54 bundles React Native 0.81.5 and React 19.1.0.
- Expo SDK 57 bundles React Native 0.86.

Running two React Native versions in one app is not an option: the JavaScript runtime, the codegen
output and the native module ABI all have to agree, and Metro would have to bundle two copies of the
runtime. So the React Native version is the binding constraint, and it is set by whichever platform
moves slowest — which is macOS.

react-native-macos 0.81.9 declares a peer dependency on react-native 0.81.6 while Expo pins 0.81.5.
The two patch releases are compatible in practice, but npm will not resolve them together on its own.

## Decision

We build on **Expo SDK 54 with React Native 0.81.5 and React 19.1.0**, pinned across every workspace.
The react-native version is forced to 0.81.5 through an `overrides` entry in the root `package.json`
so that react-native-macos resolves against the same runtime the rest of the app uses.

Expo module versions follow SDK 54's bundled list exactly, rather than whatever npm considers latest.

## Consequences

- We are a major SDK version behind and will stay there until react-native-macos ships a newer React
  Native. Anything that requires a later Expo or React Native — new architecture features, newer
  Expo modules — is out of reach until then.
- The SDK bump, when it comes, is a single coordinated move across all four platforms. It should be
  planned as its own piece of work, not slipped into a feature branch.
- Libraries that only support the new architecture on recent React Native versions (Reanimated 4,
  FlashList 2, MMKV 3) are held back until they are verified against react-native-macos. The
  transcript list starts on a plain inverted `FlatList` behind an abstraction so that swapping it
  later does not reach into the rest of the app.
- The `overrides` entry has to be revisited on every dependency bump. If react-native-macos and Expo
  ever disagree by more than a patch release, the override stops being safe and this record needs a
  successor.
